# RK3588 开发板：交接唤醒与单 IP 容量后续实测

2026-11-15，延续[上一轮定位](r8169-multi-queue-performance.md)。用户约束为：
保持 main CPU4、四个 A55 worker CPU0–3，兼顾多客户端，保持既有 NAT 行为。
此次没有使用 A76 worker，没有修改 NAT worker 归属规则、用户限额、会话语义或防火墙规则。

## 已保留：0019 发布/休眠握手

0018 解决了“已取出交接帧，却在分发前休眠”的确定性问题，但仍有另一个窗口：
生产方发布新工作时消费方尚未宣布休眠，生产方可能不写唤醒 eventfd；随后消费方
宣布休眠，未重新检查新工作便进入等待。原来仅在队列空→非空时通知的条件也不够稳妥。

0019 在生产方发布每批帧后执行屏障并检查唤醒；唤醒仍由 `wakeup_pending` 合并，
不产生逐包通知。在消费方宣布休眠后执行配对屏障，再次检查待分发帧和新的交接工作。
队列容量与丢包策略不变。回归检查以确定性交错在初次检查之后注入交接工作：
0018 单独使用时失败，0019 通过；无工作时仍允许等待。

同 PMD、四 A55，64B 含 FCS，物理 LAN→动态 SNAT→物理 WAN VLAN100，
每档指定包数为 PPS×10，mlx5 DPDK 接收端按唯一序号计数。

| 单流跨 worker、adaptive | 输入 Mpps | 唯一实收 Mpps | NAT 交接拥塞增量 |
|---|---:|---:|---:|
| 第一次 | 0.5 | 0.499976 | 0 |
| 第二次 | 0.5 | 0.500000 | 0 |
| 第三次 | 0.5 | 0.500000 | 0 |
| 单流高负载 | 1.0 | 0.847950 | 0 |

这三次没有复现原约 0.14%–0.15% 的单流交接丢包。第一档仍有 242 个唯一序号缺失，
不伴随交接丢包；不能宣称全路径长期无损，也不能将该结论推广到多流高负载。
单 IP、1 万流在 0.5 Mpps 档仍有 11,347 个交接拥塞计数增量，属于另一负载条件。

## 未解决：单 IP、1 万流的四 A55 容量

0019 后，单 IP、1 万流在 1 Mpps 输入时，adaptive 实收约 0.629/0.650 Mpps，
polling 约 0.696 Mpps；提高唤醒可靠性没有消除这个容量限制。

对两个 adaptive 1 Mpps 多流阶段采样 NAT worker 0 的用户态 IP，8 秒、约 1 kHz，
分别取得 7692、7709 个样本，丢样为零。按当时的进程映射聚合：

| 对象 | 第一次样本占比 | 第二次样本占比 |
|---|---:|---:|
| r8169 PMD | 26.8% | 28.0% |
| ACL 插件 | 21.4% | 22.8% |
| NAT44-EI 插件 | 17.0% | 16.3% |
| libvnet | 15.0% | 14.6% |
| libvlib | 12.5% | 10.3% |

NAT worker 接近满核，但查 NAT 表不是唯一热点；它还承担接收、转发、ACL、发送和回收。
同源 IP 的 NAT 工作仍集中到一个 worker，四个 RX 队列不会自动使这部分工作四核并行。
这里证明的是当前路径的容量瓶颈，不能据此断言未来不存在兼容优化空间。

后续优化：NAT 后把包交回收包 worker，单 IP 1 Mpps 实收提高到约 0.94–0.99 Mpps，见
[return handoff](rk3588-return-handoff.md)。

## 试验一：遵循配置的 L3 RSS（未保留）

当前生产构建的 PMD 启动时强制开启全部 L4 RSS 类型，虽然配置为 `rss { ipv4 ipv6 }`。
将仓库已有的 RSS 配置补丁叠加到生产源树，可以使驱动遵循配置。
单源 IP 与目的地址固定时，1 万源端口流会集中到一个 RX 队列。

| 条件 | 输入 Mpps | 唯一实收 Mpps |
|---|---:|---:|
| 单 IP 多流，RX 与 NAT 同 worker | 1.0 | 0.509/0.517 |
| 单 IP 多流，跨 worker | 1.0 | 0.795 |
| 单 IP 多流，默认映射 adaptive | 1.0 | 0.800 |
| 16 IP 多流，adaptive | 1.5 | 0.863/0.867 |
| 16 IP 多流，polling | 1.5 | 1.430 |

这不是兼顾多客户端的有效优化，已恢复原 PMD。RSS key 在重启时随机生成，
同 IP 的 RX/NAT 是否对齐也可能变化，不能用单个有利映射宣称容量瓶颈已解决。
此处未修改仓库已有的 RSS 功能补丁；撤回的是此次设备部署试验。

## 试验二：定向队列中断通知（未保留）

候选实现让 RX 清状态前保存该队列的可能原因，处理 IRQ 时只通知有硬件或软件
原因的队列。保存原因不依赖清状态前读到的位，覆盖 DMA 与 W1C 并发的窗口。
队列模型及 RX DMA、TX 回收检查通过，实机吞吐未满足目标：

| 条件 | 输入 Mpps | 唯一实收 Mpps |
|---|---:|---:|
| 单 IP 多流，adaptive | 1.0 | 0.637/0.612 |
| 单 IP 多流，polling | 1.0 | 0.696 |
| 16 IP 多流，adaptive | 1.5 | 1.123/1.119 |
| 16 IP 多流，polling | 1.5 | 1.484 |

未观察到单 IP 容量收益，多客户端 adaptive 也不理想，已恢复原 PMD。
候选补丁与测试仅归档在试验目录，没有加入生产补丁系列。
温度/频率日志显示该次测试 A55 为 1.8 GHz，DDR 为 2112 MHz，温度约 44℃，
未观察到测试期间热降频。
