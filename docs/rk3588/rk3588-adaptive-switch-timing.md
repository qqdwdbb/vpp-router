# RK3588 开发板：adaptive 收包的切换时间

2026-11-26 实测。配置：单 worker 在 A55 cpu2（performance，1.8 GHz），wan0、lan0（RTL8125）
各一个 RX 队列、均为 adaptive；带 0022（`busy-loops 16`）、0023、0024、0027。测量期间有正常的家庭流量
（几百到 8 kpps）。

## 切换规则

vlib 每次调度 adaptive 输入节点后看上一个统计窗口（128 轮主循环）的向量数：

- 中断态下窗口 ≥10 个向量：当次切到轮询。
- 轮询态下窗口 ≤5 个向量：先标记，下一次调度（驱动在这次武装中断，见 0024）再切到中断；
  中间出现忙窗口就取消标记（0023）。

窗口按轮数而不是时间计。轮询时一轮不到 1 µs，128 轮约 150 µs；中断态下线程大部分时间在睡，
一次唤醒只跑一两轮，同样 128 轮可能是几毫秒。

## 方法

打开 `event-logger trace dispatch`（只记录收到包的调度，环扩到 1M 条，测完恢复 131072），
从局域网测试机向路由器的 UDP 9 端口发 64B 突发：2、20、100、300 kpps，每档 0.2–0.5 秒，中间停 1 秒。
从日志取 dpdk-input 每次调度的收包数和 `switching to polling/interrupt` 事件的时间戳。
日志本身给每次调度增加少量开销。300 kpps 一档只记录到开头，环就满了。

## 结果

从突发开始到切到轮询：

| 输入 | 切到轮询前 | 期间中断态处理的包 | 之后 |
|---|---|---|---|
| 100 kpps | 4.3 ms | 455 | 整个 300 ms 一直轮询（29,607 包） |
| 300 kpps | 6.8 ms | 2,100 | 轮询 |
| 20 kpps | 9.6 ms | 200 | 来回切换：每约 8 ms 轮询约 0.5 ms（约 11 包），每秒约 125 次 |
| 2 kpps 及背景流量 | — | — | 每几十毫秒切到轮询约 155 µs，没收到包就切回 |

切到轮询之前，中断态约每 80 µs 被唤醒一次、每次取 8 个包（100 kpps），300 kpps 也在中断态下接住，
lan0、wan0 都没有 `rx missed`。

从最后一个包到标记切回中断：150–170 µs，即一个轮询窗口；真正切换在下一次调度，约 1 µs。

稀疏 ping（测试机 → 路由器自己的地址，每 0.2 秒一个，300 个）：

| 模式 | 最小 | p50 | p90 | p99 | 最大 |
|---|---|---|---|---|---|
| adaptive | 0.122 | 0.255 | 0.283 | 0.489 | 0.674 ms |
| polling | 0.067 | 0.085 | 0.099 | 0.128 | 0.226 ms |

worker 睡着时，第一个包的唤醒约多 0.17 ms（中位数）。空闲时 worker 约 2–3% CPU，polling 为 100%。

## x86 对照：ConnectX-3 主机

同日在 ConnectX-3 主机（i5-9300H，intel_pstate powersave，C 态最深 C10，退出延迟 890 µs）上用同样方法测。
为排除路由器转发造成的成批到达，测试机经交换机在 VLAN 2 上直接向 port0.2 所在网桥的 BVI MAC 发
原始帧（ethertype 0x88b5，进 dpdk-input 后丢弃）。

窗口同样按 128 轮计，但 x86 循环快得多：有包轮询时一个窗口只有约 15 µs。300 kpps 时一个窗口约 4 个包，
不到 6 个就算空闲，约 57 µs 后切回中断。结果是 300 kpps 以下 adaptive 基本一直在中断态：

| 输入 | 轮询占时间 | 每秒切到轮询 | 中断态每次唤醒取包 | worker CPU（adaptive / polling） |
|---|---|---|---|---|
| 20 kpps | 0.2% | 136 | 1.0 | 36% / 100% |
| 100 kpps | 0.9% | 556 | 1.1 | 66% / 100% |
| 300 kpps | 5.4% | 713 | 1.8 | 94% / 100% |

负载更高时会稳定轮询（测试机多进程并发发送，单队列，环满前约 90–150 ms）：494 kpps 轮询占 93.9%，
968 kpps 94.6%，1382 kpps 92.1%，每秒切到轮询 9–33 次；剩下的时间主要是每段开头切到轮询前那几毫秒。
x86 上的分界在 300–500 kpps 之间。测试帧在 ethernet-input 就丢弃，每包开销很小；实际转发（NAT 等）
每包更贵、每轮更慢、窗口更长，分界会更低。

丢包按发送数与 port0.2 收包计数逐个对账（测试 VLAN 上没有其他流量，测试机网卡 tx_dropped 不变）：
adaptive 和 polling 在 20、100、200、300 kpps 及约 0.5、1、1.5 Mpps 各持续 2 秒，以及 20 次
"200 kpps 发 20 ms、停 30 ms"（每段都要切换），全部 0 丢包。高于约 1.5 Mpps（发送端上限）和实际转发负载没有测。
测试机上的临时 VLAN 接口要先关掉 IPv6：否则它从网桥收到 RA，自动配地址，把测试机自己的 IPv6 流量
送进被测机（约 50 包/秒），计数就不准了。

中断态下约每 4.5 µs 被唤醒一次，几乎一包一次；300 kpps 时 CPU 已接近轮询，节省的只是唤醒开销之外的空转。
没有丢包。经路由器转发时，到达本身就是约 50–95 µs 一批，窗口里没有包，同样很快切回中断。

稀疏 ping（经路由器转发，看差值）：adaptive p50 1.050 ms，polling 0.458 ms，唤醒约多 0.57 ms。
持有 `/dev/cpu_dma_latency` = 0（禁止深 C 态）后 adaptive p50 0.492 ms，只多约 0.03 ms：x86 的唤醒延迟几乎全是
C 态退出。RK3588 开发板上唤醒约多 0.17 ms。

## 实验：按线程 CPU 判断切换（未采用）

2026-11-26 试过一个 vlib 补丁，把 adaptive 的判断从"128 轮主循环里的向量数"改成按线程 CPU：
中断态下连续两个 1 ms 窗口里线程用了至少 90% 的 CPU（`CLOCK_THREAD_CPUTIME_ID`，含内核时间，扣掉在 worker 屏障上
空转的时间）就切到轮询；轮询时处理包的时间占比降到进入后第二个窗口的一半以下并持续 2 ms 就切回中断；另外每轮询
100 ms 回中断态重测一次（重测后 50 ms 内又进轮询则间隔加倍，最长 1.6 s）。想法是让判断与 CPU 快慢无关：唤醒的
开销接近轮询时才轮询。在 ConnectX-3 主机和 RK3588 开发板上都没有收益，补丁没有保留。

### ConnectX-3 主机

纯中断态（阈值设成到不了）的线程 CPU：50 kpps 约 34%，100 kpps 约 65%（1 ms 窗口 p90 70%、最高 89%），
150 kpps 约 83%，200 kpps 约 89%，300 kpps 约 91%。每次唤醒取的包随负载变多，中断态的 CPU 在约 90% 处趋平。

与原规则对比（直连 VLAN 2，逐包对账）：

| 输入 | 原规则 wk0 CPU | 按 CPU 判断 wk0 CPU | 丢包 |
|---|---|---|---|
| 空闲 | 2% | 1% | — |
| 20 kpps | 32% | 40%（中断） | 0 / 0 |
| 100 kpps | 67% | 66%（中断，6 秒内 4 次短暂进轮询、100 ms 内重测退出） | 0 / 0 |
| 200 kpps | 88% | 102%（轮询） | 0 / 0 |
| 300 kpps | 94% | 101%（轮询，开始后约 6 ms 切到轮询） | 0 / 0 |
| 0.5 / 1 Mpps | 97% / 101% | 101% / 101% | 0 / 0 |

进轮询的点从约 400 kpps 移到约 200 kpps，换来 200–300 kpps 时多 7–14 个百分点的 CPU；这个区间原规则的中断态
约每 4.5 µs 唤醒一次，延迟收益很小；切到轮询仍要约 6 ms，因为 300 kpps 的中断态 CPU 只比阈值高一点。

| 50 kpps | 101% / 0.055 / 0.14 / 0 | 43% / 0.134 / 8.1 / 0 | 40% / 0.141 / 1.2 / 0 |

r8169 中断态约 80 µs 唤醒一次、每次取很多包，A55 在中断态到 300 kpps 也只用 53–68% CPU，到不了阈值，基本不进

### 中断态约 10 ms 的停顿：VPP 的 CPU 上有其他进程

同日追查上面的 RTT 尖峰。开发板空闲时每 5 ms ping 一次，每 4000 个有几次超过 5 ms，最长 10–18 ms。

- dispatch 跟踪：尖峰那一刻开发板 12.9 ms 里一个包也没处理，随后一次取 2 个（期间到的两个 ping 都在收包环里）；
  worker 上单次调用最长的节点只有约 0.2 ms（`show runtime max`），停顿期间也没有屏障，不是某个节点或 CLI 占住了 worker。
- 发送端：测试机上的 python 自己记录，没有超过 1 ms 的停顿。
- 三台机器两两 ping、同时 ping 按时间戳对齐，尖峰在三条路径上同一时刻出现。这三条路径都经过开发板：交换机
  2 口接开发板 eth2，ConnectX-3 主机直连开发板 eth1，由 VPP 的 L2 桥接入局域网。所以是开发板，不是交换机。
- ftrace（网卡中断、`dpdk-intr` 和 worker 的唤醒与上 CPU）：一类是网卡中断后 `dpdk-intr`（DPDK 的中断线程，
  和主线程一起在 cpu1）最长 7.6 ms 才运行，当时 cpu1 上在跑 vpp-egress-gate、sing-box；另一类是 worker 被唤醒后
  最长 10 ms 才运行，cpu2 上在跑其他进程。开发板没有隔离 CPU，heproxy、charon、nebula、sing-box 等服务
  也在 VPP 的 CPU 上运行；worker 在中断态睡下后它们就占用 cpu2。

运行时对照（每 5 ms ping 一次，8000 个一组，用 `taskset` 挪进程、`chrt` 改优先级，测完还原）：

| 条件 | p99.9 | 最大 | 超过 5 ms |
|---|---|---|---|
| 现状 | 2.0–8.2 ms | 10.4–14.6 ms | 2–13 |
| 只把 `dpdk-intr` 设成 SCHED_FIFO | 0.7–1.6 ms | 4.9–12.4 ms | 0–3 |
| 其他进程移出 cpu1、cpu2，`dpdk-intr` FIFO | 0.41 ms | 0.75 ms | 0（两组） |
| 其他进程只移出 cpu2，`dpdk-intr` FIFO | 0.41–0.48 ms | 0.76 ms | 0（三组） |

主线程的 CPU 不用独占：主线程只跑控制面，`dpdk-intr` 设成实时优先级后就不再被普通进程耽误。worker 不能设
实时优先级：它在负载高时轮询、占满 CPU，会被内核实时限流（每秒停 50 ms）。安装脚本据此在有 worker 时
（`corelist-workers`）把 systemd 的默认 CPU 亲和性设成 worker 以外的 CPU（`/etc/systemd/system.conf.d/90-vpp-router-cpu.conf`，
`vpp-router.service` 自己用全部 CPU），`vpp-router-ctl post` 把已经在运行的进程挪走并把 `dpdk-intr` 设成
SCHED_FIFO 10。

### 结论和教训

- 两个平台上决定该不该轮询的是延迟，不是 CPU：x86 中断态的 CPU 在约 90% 趋平，r8169 中断态很省 CPU。
  原规则按包数判断，在 RK3588 开发板上 50 kpps 就轮询，突发进来时收包环不会满。
- 只换 libvlib 时不能给 `vlib_main_t` 加字段：主线程的 `vlib_main_t` 由 `vlib_main_init` 分配，它是内联在 vpp
  程序里的，按 vpp 编译时的大小分配。第一版把每线程状态加在 `vlib_main_t` 末尾，一打开功能 CLI 就写越界，
  堆被破坏，主线程在 `mallinfo` 里死循环，VPP 卡死。
- 按 CPU 判断要扣掉 worker 在屏障上空转的时间，否则每条 CLI/API 命令都像负载；突发开始时的升频
  （intel_pstate powersave）也会让前几个窗口偏高。

## 动态调频与冷启动突发（2026-11-27）

后续按 RX burst 请求异步升频、保持 100 ms 的独立补丁及延迟测量，见
[0049：RX burst 触发异步升频](rk3588-rx-burst-dvfs.md)。以下保留固定最低频率保护的验证过程。

本次目标是保留空闲降频，并解决升频期间处理能力不足造成的缺包。RK3588 开发板的 6.1.57 内核调用 `uclampset` 返回
`Operation not supported`。A76 空闲 408 MHz 时，短时 CPU 负载在 ondemand 下约 17–20 ms 才到最高频率；
直接用 userspace 写最高频率也耗时约 6.6–7.9 ms。schedutil 配合短时 RT 唤醒约 6.7 ms，降低
`rate_limit_us` 没有消除该延迟。以上是本机短测，不能直接当成网卡模式切换耗时。

因此采用经过负载验证的**最低频率保护**：让 worker 在升频期间也有足够的处理能力，保留原最高频率和动态 governor。
`vpp-system` 保存每个 cpufreq policy 的请求下限及首次启用前的下限，支持立即设置、撤销和启动后恢复；
`vpp-router-ctl prep` 在 VPP 开始收包前恢复下限。sysfs 的限制更新可能异步完成，需要有界读回等待；内核暂时
施加更高的有效下限时，仍满足保护要求。不会在收包或模式切换路径里执行频率写入。

### 隔离收包测试

Linux 测试机四个进程发送 64B IPv4/UDP 帧（含 FCS），每次 20 ms、间隔 600 ms，每组 8 次。
在被测 VPP 内为 TEST-NET 地址临时加独立丢弃路由，用该路由的包计数逐包对账，避免背景流量污染计数。
这部分经过收包和 IPv4 查表，**没有经过 NAT 转发**；完成后删除临时路由、接口，并恢复原 CPU 布局和调频设置。

## 发现的问题：切回 adaptive 后停在轮询（0046）

测试中把 lan0、wan0 设为 polling，再按 lan0、wan0 的顺序设回 adaptive，dpdk-input 一直是 polling，
0 向量/次，worker 100% CPU。原因见 [0046](../../patches/README.md)：最后改回 adaptive 的队列
不是索引最大的那个时，vnet 判断没有变化，节点没有拿到 adaptive 标志。面板“系统”页单独切换一个口的
收包方式就能触发。当时先设为 interrupt 再设回 adaptive 恢复。ConnectX-3 主机上按同样条件
（port0 最后改回）复现，装上 0046 后三种顺序都回到中断态、worker 0%。

同日部署到 RK3588 开发板：先不打补丁重编 libvnet，`.text`、`.rodata`、`.data`、`.eh_frame` 与已装文件相同，
再打 0046 重编，由一次性脱离运行的部署脚本替换并重启 VPP（失败则回退），重启后 3 秒健康检查通过。
之后重复 lan0、wan0 设为 polling 再按 lan0、wan0 设回 adaptive，dpdk-input 回到中断态，worker 约 2%。
